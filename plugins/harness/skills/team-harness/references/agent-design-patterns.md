# Agent Team Design Patterns

## Execution Modes

### Agent Teams (기본, 최우선 선택)
독립적인 Claude Code 인스턴스를 팀원으로 생성. `SendMessage`로 직접 통신, `TaskCreate`/`TaskUpdate`로 공유 작업 목록 조율.

- 팀원 간 실시간 정보 교환과 교차 검증 가능
- 세션당 1개 팀만 활성 (중첩 불가)
- Phase 전환 시 `TeamDelete` → 새 `TeamCreate`

### Sub-agents (경량 대안)
메인 에이전트가 `Agent` 도구로 직접 호출. 결과는 호출자에게만 반환.

- 에이전트 간 직접 통신 불가
- 토큰 효율적이지만 협업 제한
- `run_in_background: true`로 병렬 실행 가능

### Hybrid (고급)
Phase마다 다른 실행 모드 사용. 각 Phase 상단에 실행 모드를 명시.

**모드 전환 규칙:**
- 팀 → 서브: `TeamDelete` 후 `Agent` 호출
- 서브 → 팀: 서브 에이전트 파일 산출물을 팀원에게 `Read` 경로로 전달
- 팀 → 팀: 이전 팀 정리 후 새 `TeamCreate`

### 판단 프레임워크

| 질문 | 결과 |
|------|------|
| 2+ 에이전트 + 상호 통신 필요? | Agent Teams |
| 결과만 전달하면 충분? | Sub-agents |
| 단일 에이전트? | 팀 불필요 |

## 6 Core Architecture Patterns

### 1. Pipeline (파이프라인)
순차적 핸드오프. 각 단계가 이전 출력에 의존.

```
[분석] → [설계] → [구현] → [검증]
```

- 각 단계에 1명의 주 담당자
- 팀 모드: 제한적 (병목 가능)
- 적합: 명확한 순서가 있는 워크플로우

### 2. Fan-out/Fan-in (팬아웃/팬인)
병렬 분석 → 결과 통합. **가장 자연스러운 팀 패턴.**

```
        ┌→ [전문가 A] ─┐
[분배] ─┼→ [전문가 B] ─┼→ [통합]
        └→ [전문가 C] ─┘
```

- 팀원들이 발견을 공유하고 도전하면서 품질 향상
- 팀 모드 필수: 실시간 교차 검증이 핵심 가치
- 적합: 다관점 리서치, 코드 리뷰, 보안 분석

### 3. Expert Pool (전문가 풀)
라우터가 입력 유형에 따라 적절한 전문가 선택.

```
[라우터] ──→ [보안 전문가] (보안 이슈)
         ──→ [성능 전문가] (성능 이슈)
         ──→ [테스트 전문가] (테스트 이슈)
```

- 서브 에이전트가 더 효율적 (필요한 전문가만 호출)
- 적합: 요청 유형이 다양하고 전문 영역이 명확한 경우

### 4. Producer-Reviewer (생성-검증)
생성과 검증을 쌍으로 구성. 실시간 피드백으로 재작업 최소화.

```
[생성자] ⇄ [검증자] (최대 2-3회 루프)
```

- 팀 모드 강점: 실시간 피드백 교환
- 최대 재시도 횟수 설정 필수 (무한 루프 방지)
- 적합: 품질 게이트가 필수인 작업

### 5. Supervisor (감독자)
중앙 에이전트가 런타임 조건에 따라 동적으로 작업 분배.

```
[감독자] → 파일 분석 → 배치 할당
    ├→ [작업자 1] (batch A)
    ├→ [작업자 2] (batch B)
    └→ [작업자 3] (batch C)
    ← TaskUpdate 수신 → 추가 배치 할당
```

- 공유 작업 목록의 자체 요청(claim) 기능과 자연스럽게 매칭
- 팬아웃과의 차이: 작업이 사전 고정이 아니라 런타임에 동적 할당
- 적합: 작업량이 불균일하거나 예측 불가한 경우

### 6. Hierarchical Delegation (계층적 위임)
재귀적 작업 분해. 하위 팀으로 위임.

```
[총괄] → [프론트팀] → [컴포넌트 A, B]
       → [백엔드팀] → [API, DB]
```

- **2레벨 제한** (팀은 중첩 불가, 평탄화 필요)
- 깊은 구조는 지연과 컨텍스트 손실 유발
- 적합: 대규모 프로젝트의 도메인별 분할

## Composite Patterns (복합 패턴)

실제 시나리오는 여러 패턴을 결합:
- "병렬 번역 + 각각 개별 리뷰" (Fan-out + Producer-Reviewer)
- "분석 → 병렬 구현 → 순차 통합 테스트" (Pipeline + Fan-out + Pipeline)

**원칙**: 에이전트 간 통신이 품질을 좌우하는 복합 패턴에서 Agent Teams 사용.

## 4-Axis Separation Criteria (분리 기준)

에이전트를 별도로 분리할지 판단하는 4가지 축:

| 축 | 질문 | 분리 기준 |
|----|------|----------|
| **전문성** | 도메인 지식이 다른가? | 보안 vs 성능 vs 테스트 → 분리 |
| **병렬성** | 독립 실행 가능한가? | 의존성 없음 → 분리하여 병렬화 |
| **컨텍스트 범위** | 컨텍스트 부하가 높은가? | 각자 긴 문서 분석 → 분리 |
| **재사용성** | 다른 팀/세션에서 쓸 수 있는가? | 범용 QA → 분리하여 재사용 |

## Agent vs Skill 구분

| 측면 | Agent | Skill |
|------|-------|-------|
| **목적** | 전문가 페르소나 + 행동 원칙 | 절차적 지식 + 도구 번들 |
| **위치** | `agents/{name}.md` | `skills/{name}/SKILL.md` |
| **트리거** | 명시적 `Agent` 도구 호출 | 키워드 매칭 자동 로딩 |
| **초점** | "누가 하는가" | "어떻게 하는가" |
| **재사용** | 세션/팀 단위 | 어떤 에이전트든 참조 가능 |

## Agent Definition Structure

모든 에이전트는 `agents/{name}.md` 파일로 정의. 빌트인 타입도 파일 생성 권장 (세션 지속성, 협업 명확성).

### Required Sections
1. 역할 요약과 트리거
2. 핵심 책임 (Core Responsibilities)
3. 작업 원칙 (Work Principles)
4. 입력/출력 프로토콜 (I/O Protocol)
5. 에러 핸들링 (Error Handling)

### Team Mode Addition
팀 모드 에이전트는 추가로:
```markdown
## Team Communication Protocol
- **SendMessage 대상**: [구체적 동료와 시나리오]
- **Task 할당 패턴**: [생성/요청하는 작업 유형]
- **공유 작업 요청**: [특정 에이전트에게 도움 요청 방법]
- **데이터 접근**: [Read로 접근하는 _workspace/ 파일]
```

### Model Requirement (opus 필수)

모든 팀 에이전트의 `Agent()` 호출과 `TeamCreate` 멤버 정의에 `model: "opus"`를 명시한다.

| 원칙 | 이유 |
|------|------|
| **전 에이전트 opus 강제** | 팀 협업 품질은 모델 추론 능력에 직결. 약한 모델이 팀에 섞이면 전체 산출물 품질이 하락 |
| **비용보다 품질 우선** | 팀 작업은 본질적으로 복합/고난도이므로 비용 절감보다 결과 품질이 우선 |
| **일관성 보장** | 동일 모델 사용으로 팀원 간 추론 수준 편차 제거 |
