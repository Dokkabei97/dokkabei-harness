## 1. 6 Core Architecture Patterns (기본 패턴 6종)

### 1-1. Pipeline (파이프라인)

작업을 정해진 순서대로 이어 간다. 이전 에이전트의 출력이 다음 에이전트의 입력이 된다.

```
[분석] → [설계] → [구현] → [검증]
```

- 각 단계에 1명의 주 담당자
- **적합:** 명확한 순서가 있고 각 단계가 이전 산출물에 크게 의존할 때
- **예시:** 소설 집필 — 세계관 → 등장인물 → 줄거리 → 집필 → 편집
- **주의:** 한 단계가 늦어지면 전체가 늦어진다(병목). 각 단계는 가능한 한 독립적으로 설계한다.

**v2 권장 실행 모드:** 단계와 항목을 미리 나열할 수 있으면 **A 워크플로 조율**의 `pipeline()`을 쓴다. 각 항목은 앞 단계가 끝나는 대로 다음 단계로 넘어가므로, 한 단계의 모든 항목을 기다릴 필요가 없어 전체 실행 시간이 짧아진다. 단계 사이마다 사람이 산출물을 검토해야 한다면 **C 서브에이전트**를 차례로 호출한다.

### 1-2. Fan-out/Fan-in (팬아웃/팬인)

서로 독립적인 작업을 동시에 처리한 뒤 결과를 하나로 합친다.

```
        ┌→ [전문가 A] ─┐
[분배] ─┼→ [전문가 B] ─┼→ [통합]
        └→ [전문가 C] ─┘
```

- **적합:** 같은 입력을 여러 관점·영역에서 각각 분석해야 할 때 — 다관점 리서치, 코드 리뷰, 보안 분석
- **예시:** 종합 조사 — 공식 자료·언론·커뮤니티·배경을 동시에 조사한 뒤 하나의 보고서로 정리
- **주의:** 결과를 합치는 방식(통합 단계)이 전체 품질을 좌우한다.

**v2 권장 실행 모드:** **A 워크플로 조율**을 먼저 고려한다. 관점 목록을 배열로 정의해 `pipeline()`으로 보내고, `schema`에 맞춰 결과를 받은 뒤 코드로 합친다. 모든 결과를 모은 뒤 중복을 제거해야 할 때만 `parallel()` 장벽을 쓴다. 조사자가 찾은 내용을 실시간으로 공유·반박해야 하는 2~4명 규모라면 **B 지속형 에이전트 협업**도 알맞다.

### 1-3. Expert Pool (전문가 풀)

라우터가 입력 유형에 맞는 전문가만 골라 호출한다.

```
[라우터] ──→ [보안 전문가] (보안 이슈)
         ──→ [성능 전문가] (성능 이슈)
         ──→ [테스트 전문가] (테스트 이슈)
```

- **적합:** 요청 유형이 다양하고 전문 영역이 명확할 때
- **예시:** 코드 검토 — 보안·성능·아키텍처 전문가 가운데 해당 영역만 호출
- **주의:** 라우터가 입력을 잘못 분류하면 알맞은 전문가를 선택할 수 없다.

**v2 권장 실행 모드:** **C 서브에이전트 위임**으로 필요한 전문가만 한 번 호출한다(상시 대기 불필요). 같은 전문가와 후속 대화를 이어 가야 한다면 `name`을 붙여 **B 지속형**으로 전환한다.

### 1-4. Producer-Reviewer (생성-검증)

생성 에이전트와 검증 에이전트가 한 조로 작업한다.

```
[생성자] ⇄ [검증자] (최대 2-3회 루프)
```

- **적합:** 품질 게이트가 필수이고 객관적인 판정 기준을 정할 수 있을 때
- **주의:** 최대 재시도 횟수(2~3회) 설정 필수 — 무한 루프 방지

**v2 권장 실행 모드:** 검증 기준을 코드로 나타낼 수 있으면 **A 워크플로 조율**로 아래 적대적 검증 패턴을 적용한다(찾은 항목마다 병렬 검증). 주관적 판단을 조율해야 한다면 생성자와 검증자를 **B 지속형 에이전트 한 쌍**으로 이름 붙여 실행하고 `SendMessage`로 피드백을 주고받는다. 생성자가 이전 대화 내용을 유지하므로 지적받은 부분만 정확히 고칠 수 있다.

> 세션을 넘어 "게이트 그린까지" 반복하는 maker/checker 루프(Stop훅 엔진·verified 마커)는 이 패턴의 확장이다 — [loop-harness-guide.md](loop-harness-guide.md) 참조.

### 1-5. Supervisor (감독자)

중앙 에이전트가 작업 상태를 관리하고 런타임 조건에 따라 작업을 동적으로 나눈다.

```
[감독자] → 파일 분석 → 배치 할당
    ├→ [작업자 1] (batch A)
    ├→ [작업자 2] (batch B)
    └→ [작업자 3] (batch C)
    ← TaskUpdate 수신 → 추가 배치 할당
```

- **적합:** 작업량이 불균일하거나 예측 불가해, 실행 중에 분배를 결정해야 할 때
- **팬아웃과의 차이:** 팬아웃은 시작 전에 배분을 고정하고, 감독자는 진행 상황을 보며 다시 배분한다.
- **주의:** 작업을 너무 잘게 나누면 감독자가 자주 재배분해야 하므로 병목이 된다.

**v2 권장 실행 모드:** **B 지속형 에이전트 협업**. 리더(메인 에이전트)가 `TaskCreate`로 작업을 등록하고, 작업자의 완료 알림을 받은 뒤 `SendMessage`·`TaskUpdate`로 재배분한다. 공유 작업 목록이 이 패턴과 자연스럽게 맞물린다. 작업 목록을 미리 확정할 수 있고 배분 절차도 코드로 쓸 수 있다면 **A 워크플로 조율**로 전환한다 — 그 경우 감독자가 따로 판단할 일이 없다.

### 1-6. Hierarchical Delegation (계층적 위임)

위임받은 에이전트가 다시 하위 에이전트에게 일을 맡긴다(재귀적 분해).

```
[총괄] → [프론트 담당] → [컴포넌트 A, B]
       → [백엔드 담당] → [API, DB]
```

- **적합:** 대규모 프로젝트를 도메인별로 자연스럽게 상위/하위 작업으로 나눌 수 있을 때
- **주의:** **2레벨 제한 권장.** 3단계 이상 깊어지면 지연과 컨텍스트 손실이 커진다.

**v2 권장 실행 모드:** 워크플로를 중첩한다. 상위 워크플로가 `workflow(nameOrRef, args)`로 하위 워크플로를 호출하며, 중첩은 한 단계만 지원하므로 과도한 깊이가 구조적으로 막힌다. 또는 계층을 평탄화해 단일 워크플로의 `phase()`로 다시 구성한다.

## 2. Quality Verification Patterns (품질 검증 패턴)

산출물의 정확성이 중요한 하네스에 추가하는 워크플로 검증 패턴이다. 얼핏 맞아 보이지만 실제로는 틀린 결과를 걸러내는 것이 목적이다.

| 패턴 | 구조 | 사용할 때 |
|------|------|------|
| **적대적 검증** | 찾은 항목 한 건마다 독립 검증 에이전트 N명을 실행. 과반이 근거 충분(`confirmed`)으로 판정한 항목만 통과 | 찾은 내용·주장을 신뢰할 수 있어야 할 때(검토·감사·조사) |
| **관점 분산 검증** | 검증 에이전트 N명에게 같은 프롬프트 대신 정확성·보안·재현성처럼 서로 다른 관점을 맡김 | 오류 유형이 여럿일 때 — 같은 검증의 반복이 놓치는 오류를 찾는다 |
| **심사위원단** | 서로 다른 접근의 시안 N개를 병렬 심사 → 최고점 시안을 바탕으로 다른 시안의 장점을 반영해 최종안 | 해법 공간이 넓은 설계·기획. 한 시안을 거듭 고치는 것보다 비교가 낫다 |
| **새 항목이 없을 때까지 반복(Loop-until-dry)** | 새로 찾은 항목이 K회 연속 0건일 때까지 탐색 반복. 기각 항목도 `seen`에 기록해 재제안 차단 | 문제가 몇 개일지 모르는 탐색(버그·이슈·경계 사례). 횟수 고정은 누락을 낳는다 |
| **여러 기준으로 탐색** | 컨테이너·내용·개체·시간처럼 서로 다른 기준의 탐색자를 병렬 실행 | 한 가지 기준만으로는 빠짐없이 찾을 수 없을 때 |
| **누락 검토** | 마지막에 "어떤 탐색 기준을 안 썼나, 검증 안 한 주장은, 안 읽은 자료는?"만 묻는 에이전트 1명 | 결과를 합치기 직전. 찾은 누락은 다음 탐색에 투입 |
| **제외한 항목 수 공개** | `top-N`·샘플링으로 범위를 제한하면 제외 수를 반드시 `log()`로 기록 | 모든 분산 실행. 밝히지 않으면 사용자는 전수 확인으로 오해한다 |

**규모 조정 원칙:** 사용자가 요청한 범위에 맞춘다. "버그 있는지 봐줘"면 소수의 탐색자 + 검증자 1명. "철저히 감사해줘"면 탐색자를 늘리고 항목마다 검증자 3~5명 + 종합 단계. 판단이 어려우면 조사·검토·감사는 꼼꼼하게, 빠른 확인은 작게 진행한다. Workflow 사용 자체는 사용자 동의가 전제이며 기본 규모는 작게 잡는다.

> 구현 예시: [workflow-recipes.md](workflow-recipes.md). Loop-until-dry는 **하나의 워크플로 실행 안의** 반복이다 — 세션 단위로 "게이트 그린까지" 도는 루프 엔진과는 층위가 다르다([loop-harness-guide.md](loop-harness-guide.md)).

## 3. Composite Patterns (복합 패턴)

실제 시나리오는 여러 패턴을 결합한다.

| 복합 패턴 | 구성 | 예시 |
|----------|------|------|
| **Fan-out + Producer-Reviewer** | 병렬 생성 후 각각 개별 검증 | 다국어 번역 — 4개 언어 병렬 번역 → 언어별 원어민 검토자 검수 |
| **Pipeline + Fan-out + Pipeline** | 순차 단계 가운데 일부를 병렬화 | 분석(순차) → 구현(병렬) → 통합 테스트(순차) |
| **Supervisor + Expert Pool** | 감독자가 상황에 맞는 전문가를 호출 | 고객 문의 — 감독자가 분류 후 알맞은 전문가에게 배정 |
| **탐색 + 적대적 검증 + 종합** | 여러 기준 탐색 → 항목별 검증 → 누락 검토 → 보고서 | 종합 코드 감사, 심층 조사 |

**원칙:** 복합 패턴에서는 **단계마다** 알맞은 실행 모드를 고른다(혼합 모드). 선택 기준은 "해당 단계의 제어 흐름을 미리 코드로 정할 수 있는가" — 예이면 A, 대화·맥락 유지가 품질을 좌우하면 B, 결과만 받으면 C. 오케스트레이터에는 단계마다 `**실행 모드:**`를 표기한다([orchestrator-template.md](orchestrator-template.md)의 혼합 모드 절).

## 4. Agent Type Selection (에이전트 유형 선택)

에이전트 유형은 Agent 도구의 `subagent_type` 또는 Workflow `agent()`의 `agentType`으로 지정한다.

### 기본 제공 유형

| 유형 | 사용 가능 도구 | 알맞은 용도 |
|------|----------|-----------|
| `general-purpose` | 전체(WebSearch, WebFetch 포함) | 웹 조사, 일반 작업, 파일 수정 |
| `Explore` | 읽기 전용(Edit, Write 제외) | 코드베이스에서 코드 위치 찾기. 검토·감사에는 쓰지 않는다 |
| `Plan` | 읽기 전용(Edit, Write 제외) | 아키텍처 설계, 구현 계획 작성 |

### 사용자 정의 유형

플러그인이면 `plugins/<plugin>/agents/{name}.md`, 프로젝트 하네스면 `.claude/agents/{name}.md`에 정의한다. 호출 시 `subagent_type: "{name}"`(플러그인 에이전트는 `"{plugin}:{name}"`) 또는 `agentType: "{name}"`. 사용할 도구와 모델은 YAML 프론트매터에서 정한다. 파일 생성은 `/create-flow`에 위임한다.

### 선택 기준

| 상황 | 권장 | 이유 |
|------|------|------|
| 역할이 복잡하고 여러 세션에서 반복 사용 | **사용자 정의 유형** | 전문가 역할과 작업 원칙을 파일로 일관되게 관리 |
| 간단한 일회성 조사·수집, 자세한 프롬프트로 충분 | `general-purpose` + 상세 프롬프트 | 정의 파일 없이 바로 사용 |
| 코드 위치만 탐색 | `Explore` | 수정 도구가 없어 잘못 고칠 위험이 없다 |
| 설계·계획만 작성 | `Plan` | 코드 변경 없이 분석에 집중 |
| 반복 사용하거나 전문 규칙이 필요한 구현 | **사용자 정의 유형** | 필요한 도구 허용 + 전문 지침 적용 |
| 여러 파일을 병렬로 수정 | 사용자 정의 유형 + `isolation: 'worktree'` | 에이전트 간 수정 충돌 방지. 작업 트리 생성 비용이 있으므로 병렬 수정 시에만 |

**원칙:** 여러 세션에서 재사용할 전문가 역할은 사용자 정의 유형 파일로 만든다. 기본 제공 유형을 그대로 쓰는 단발 작업에는 별도 정의 파일을 만들지 않는다.

**모델 정책:** 업무의 복잡도·예상 기간·자율성·응답 속도로 티어를 고른다 — **fable**(장기 자율·계획·조율), **opus**(깊은 분석·설계·코드 생성·교차 검증·창작), **sonnet**(일상·변환·수집; 애매하면 기본값). `haiku`·`inherit`·full model ID도 유효값이다. 근거 없이 전원에 같은 모델을 일괄 지정하지 말고, 선택 이유를 주석으로 남긴다. 상세: [model-selection-guide.md](model-selection-guide.md).

## 5. Agent Definition Structure (에이전트 정의 구조)

재사용할 에이전트는 `agents/{name}.md`(플러그인) 또는 `.claude/agents/{name}.md`(프로젝트) 파일로 정의한다.

### Required Sections (필수 섹션)

1. 역할 요약과 트리거 (frontmatter `description`)
2. 핵심 역할 (Core Responsibilities)
3. 작업 원칙 (Work Principles)
4. 입력/출력 프로토콜 (I/O Protocol)
5. 에러 핸들링 (Error Handling)
6. (B 지속형 멤버) `## Team Communication Protocol` / (A 워크플로 전용) 구조화 출력

### 템플릿

```markdown
---
name: agent-name
description: "역할을 한두 문장으로 설명하고 호출 조건이 되는 표현을 나열한다."
# tools: Read, Grep, Glob, Bash        ← 선택: 도구 제한(읽기 전용 검토자 등)
#                                         산출물을 고치는 에이전트에는 Write와 함께 Edit도 넣는다
# model: sonnet                         ← 업무 특성에 맞게 선택(model-selection-guide.md), 이유를 주석으로
---

# Agent Name — 역할 한 줄 요약

당신은 [도메인]의 [역할] 전문가다.

## 핵심 역할 (Core Responsibilities)
1. 역할1
2. 역할2

## 작업 원칙 (Work Principles)
- 원칙1 (이유도 함께 — 예외 상황에서도 같은 기준으로 판단하게 한다)
- 원칙2

## 입력/출력 프로토콜 (I/O Protocol)
- 입력: [어디서 무엇을 받는지 — 파일 경로, args, 이전 단계 산출물]
- 출력: [어디에 무엇을 쓰는지 — _workspace/ 경로 또는 구조화 반환값]

- **첫 보고**: 실제로 쓸 수 있는 도구 목록을 리더에게 알린다(`tools`에 적은 도구가 빠졌는지 확인용)
- **SendMessage 대상**: [이름으로 지정한 구체적 동료와 시나리오 — 전체 전송 없음]
- **메시지 수신**: [누구로부터 어떤 메시지를 받는지]
- **Task 패턴**: [공유 작업 목록에서 등록·요청·갱신하는 작업 유형]
- **데이터 접근**: [Read로 접근하는 `_workspace/` 파일, 동결된 산출물은 고치지 않고 `_v2` 새 파일로]

## 다시 호출할 때
- 이전 산출물이 있으면 읽고 개선점을 반영한다.

- [입력이 없거나 모호할 때 할 일]

## 협업

```

**워크플로 전용 에이전트(A):** `## Team Communication Protocol` 대신 "구조화 출력" 절을 넣는다. 반환할 JSON 구조를 명시하고, 최종 텍스트는 사용자에게 보내는 메시지가 아니라 **반환 데이터**라고 적는다.

**`tools`를 제한할 때 주의할 점:**

- 산출물을 고치는 에이전트에는 Write와 함께 Edit도 준다. Write만 있으면 한 줄을 고칠 때도 파일 전체를 다시 써야 하고, 산출물이 크면 에이전트가 수정을 포기하고 다른 파일에 따로 적어 우회한다 — 원래 산출물은 고쳐지지 않은 채 남는다. (반대로 checker는 Edit을 **의도적으로 빼서** 검증 대상 수정 경로를 막는다.)
- `TaskCreate`·`TaskUpdate` 같은 지연 로딩 도구는 `tools`에 적어도 실행 시 주어지지 않은 사례가 있다(Claude Code 2.1.226 관찰, 환경에 따라 다를 수 있음). 같은 지연 로딩 도구인 `SendMessage`는 주어졌으므로 경계는 분명하지 않다. 그래서 지속형 에이전트는 첫 보고에서 실제 도구 목록을 알리게 한다. 빠진 도구가 있으면 오케스트레이터가 대신 처리하거나(예: 리더가 `TaskUpdate`로 상태 갱신) `tools` 제한을 푼다.

## 6. 4-Axis Separation Criteria (분리 기준)

에이전트를 별도로 분리할지 판단하는 4가지 축:

| 축 | 질문 | 분리 | 통합 |
|----|------|------|------|
| **전문성** | 도메인 지식이 다른가? | 보안 vs 성능 vs 테스트 → 분리 | 영역이 겹치면 통합 |
| **병렬성** | 독립 실행 가능한가? | 의존성 없음 → 분리하여 병렬화 | 순차 종속이면 통합 검토 |
| **컨텍스트 범위** | 처리할 정보량이 많은가? | 각자 긴 문서 분석 → 분리 | 정보가 적고 작업이 짧으면 통합 |
| **재사용성** | 다른 팀/세션에서 쓸 수 있는가? | 범용 QA → 분리하여 재사용 | 이 팀 전용이면 통합 검토 |

## 7. Agent Reuse (에이전트 재사용 설계)

새 에이전트를 만들기 전에 기존 에이전트(`plugins/*/agents/`, `.claude/agents/`)와 역할을 비교한다. 하네스를 반복 구축하면 같은 역할의 에이전트가 이름만 달리해 쌓이기 쉽다. 기존 자산 탐색은 `SKILL.md`의 감사(Audit) 단계에서 수행한다.

| 기존 에이전트와의 관계 | 조치 |
|------|------|
| 기존 에이전트가 새 역할을 모두 포함 | 새로 만들지 않고 기존 에이전트를 호출 |
| 일부만 겹치고, 일반화하면 새 역할까지 맡을 수 있음 | 기존 에이전트를 일반화해 확장 |
| 일부 겹치지만 도메인을 의도적으로 특화 | 별도 에이전트로 신규 생성 |
| 역할 범위가 전혀 다름 | 신규 생성 |

**원칙:** 한 에이전트가 한 역할에 집중할수록 재사용하기 쉽고 중복이 줄어든다. 확장 결과 역할이 둘 이상이 되면 분리 가능성부터 검토한다.

**기존 에이전트를 확장할 때:** 그 에이전트를 호출하는 오케스트레이터의 동작도 바뀔 수 있다. 확장 전 호출처(`## Team Members` 표에 이 에이전트를 올린 오케스트레이터)를 확인하고, 넓어진 역할을 `description`에 반영한다. 확장 후에는 `/verify-flow` 구조 검증과 모의 실행으로 기존 흐름이 그대로 동작하는지 확인한다.

## 8. Agent vs Skill (스킬과 에이전트 구분)

| 측면 | Agent | Skill |
|------|-------|-------|
| **목적** | 전문가 페르소나 + 행동 원칙 | 절차적 지식 + 도구 번들 |
| **위치** | `agents/{name}.md` | `skills/{name}/SKILL.md` |
| **트리거** | Agent 또는 Workflow 도구로 명시 호출 | 요청이 `description`의 적용 조건에 맞을 때 자동 로딩 |
| **초점** | "누가 하는가" | "어떻게 하는가" |
| **재사용** | 세션/오케스트레이터 단위 | 어떤 에이전트든 참조 가능 |

### 스킬과 에이전트를 연결하는 방식

| 방식 | 구현 | 적합한 경우 |
|------|------|-----------|
| **Skill 도구 호출** | 에이전트 프롬프트에 `Skill 도구로 /skill-name 호출` 명시 | 스킬이 독립 워크플로이고 사용자가 직접 호출할 수도 있을 때 |
| **프롬프트에 직접 포함** | 에이전트 정의에 스킬 내용을 직접 작성 | 스킬이 50줄 이하로 짧고 해당 에이전트 전용일 때 |
| **참고 파일 로드** | 필요할 때만 `Read`로 스킬의 `references/` 파일을 읽음 | 스킬 내용이 많고 특정 조건에서만 필요할 때 |

여러 에이전트가 함께 쓰는 스킬은 Skill 도구로, 특정 에이전트 전용의 짧은 스킬은 인라인으로, 대용량은 필요한 참고 파일만 로드한다.
