## 1. `description` 작성 방식

Claude에 노출되는 스킬 필드는 `name`과 `description`뿐이며, Claude는 이 두 필드만 보고 스킬 사용 여부를 결정한다. 구체적인 호출 조건은 반드시 `description`에 적는다.

### 트리거 메커니즘

Claude는 기본 도구만으로 쉽게 처리할 수 있는 단순 작업에는 스킬을 호출하지 않는 경향이 있다. "이 PDF 읽어줘" 같은 요청은 `description`이 완벽해도 트리거되지 않을 수 있다. 복잡하고 다단계이며 전문적인 작업일수록 트리거 확률이 높다.

### 작성 원칙

1. **스킬이 하는 일** + **실행해야 하는 구체적 상황**을 모두 적는다. 지원 범위는 동작 단위로 열거한다.
2. 유사하지만 트리거하면 안 되는 경우가 있으면 적용 범위와 제외 조건(경계)을 명시한다. 유사 스킬과의 차별점도 여기서 드러낸다.
3. Claude가 트리거를 보수적으로 판단하는 경향을 보상하도록 약간 "pushy"하게 쓴다.
4. 여러 작업을 조율하는 스킬(오케스트레이터)에는 **후속 작업 어휘**(재실행, 수정, 보완, 이전 결과 개선)를 반드시 넣는다.
5. 핵심 사용 사례를 **앞쪽 250자 안에** 둔다 — 스킬 목록에서 뒷부분이 잘릴 수 있다(SKL-010).

### 레포 규약: 이중언어 description

본 마켓플레이스의 skill·command·agent frontmatter `description`은 **이중언어**로 쓴다.

- **한국어 원문 먼저**, 이어서 **영어 요약 + `Use when: …` 트리거 절**을 덧붙인다.
- 한국어 프롬프트와 영어 프롬프트 양쪽에서 활성화가 유지되도록 하기 위함이다.
- **총 길이 ≤ 1,400자** — 스킬 목록은 1,536자에서 잘린다.

```yaml
description: |
  PDF 파일을 읽고 텍스트·표를 추출하며 병합·분할·회전·워터마크·암호화·OCR을 수행한다.
  사용자가 .pdf 파일을 언급하거나 PDF 산출물을 요청하면 반드시 이 스킬을 사용한다.
  단순 '읽기'보다 변환·편집·분석이 필요한 작업에 특히 유용하다.
  Reads, extracts, merges, splits, rotates, watermarks, encrypts, and OCRs PDF files.
  Use when: a .pdf file is mentioned, PDF output is requested, or a PDF needs conversion/editing/analysis.
```

### 좋지 않은 예

- `"데이터를 처리하는 스킬"` — 어떤 파일·작업인지 불분명하다.
- `"PDF 관련 작업"` — 구체적 동작도, 언제 실행할지도 없다.
- 영어만 또는 한국어만 — 반대 언어 프롬프트에서 활성화가 약해진다(레포 규약 위반).

## 2. 본문 작성 방식

### Why-First — 이유부터 설명한다

LLM은 규칙이 필요한 이유를 이해하면 엣지 케이스에서도 올바르게 판단한다. 명령만 나열하기보다 맥락을 전달하는 편이 효과적이다.

**좋지 않은 예:**

```markdown
테이블 추출에는 항상 pdfplumber를 사용하라. 테이블에는 절대 PyPDF2를 사용하지 마라.
```

**좋은 예:**

```markdown
테이블을 추출할 때는 pdfplumber를 사용한다. PyPDF2는 텍스트 추출용이라
테이블의 행과 열 구조를 보존하지 못하기 때문이다. pdfplumber는 셀 경계를 인식해
구조화된 데이터를 반환한다.
```

### Generalize — 원리 수준으로 고친다

피드백이나 테스트에서 문제를 찾으면 특정 예시에만 맞는 지시를 덧붙이지 않는다. 다른 사례에도 적용할 수 있는 원칙으로 고친다.

- **과적합된 수정:** `"Q4 매출" 열이 있으면 해당 열을 숫자로 변환하라.`
- **일반화한 수정:** `열 이름에 "매출", "금액", "수량"처럼 수치를 나타내는 단어가 있으면 숫자 타입으로 변환한다. 변환할 수 없는 값은 원래 값으로 둔다.`
- **과적합된 수정:** `test_login.py에서 assert True를 제거하라.`
- **일반화한 수정:** `항상 참인 단언(tautological assertion)은 테스트 가치가 없으므로 구체적 조건을 검증하는 단언으로 교체한다.`

### 명령형 어조

"~합니다", "~할 수 있습니다" 대신 "~한다", "~하라"로 쓴다. 스킬은 AI 에이전트가 따르는 지시서다.

### Lean — 컨텍스트 절약

컨텍스트 윈도우는 공유 자원이다. 스킬 지시뿐 아니라 작업에 필요한 다른 정보도 같은 한도를 쓴다. 각 문장이 토큰 비용을 정당화하는지 자문한다.

- "Claude가 이미 아는 내용인가?" → 삭제
- "이 설명이 없으면 Claude가 실수하는가?" → 유지
- "긴 설명보다 구체적 예시 하나가 더 분명한가?" → 예시로 대체

## 3. 출력 형식 정의

산출물 형식이 중요한 스킬에는 따라야 할 구조를 명시한다.

```markdown
## 보고서 구조
다음 템플릿을 정확히 따른다.

# [제목]
## 요약
## 주요 발견
## 권장 사항
```

형식 설명은 짧게, 실제 예시를 함께 넣으면 더 효과적이다.

**다음 단계가 코드로 읽는 산출물:** 워크플로의 다음 단계가 산출물을 코드로 처리한다면 마크다운 템플릿 대신 **JSON 구조**를 명시하고, 최종 텍스트가 사용자용 메시지가 아니라 다음 단계로 넘길 반환 데이터임을 적는다. `Workflow`의 `agent()`는 `schema`로 반환 형식을 강제하므로 스킬에 정의한 구조와 스크립트의 `schema`가 일치해야 한다.

<a id="4-examples"></a>

## 4. 예시 작성법

구체적 예시는 긴 설명보다 규칙을 분명하게 전달한다.

```markdown
## 커밋 메시지 형식

**예시 1:**
입력: JWT 토큰을 사용하는 사용자 인증 추가
출력: feat(auth): JWT 인증 구현

**예시 2:**
입력: 로그인 페이지에서 비밀번호 표시 버튼이 동작하지 않는 버그 수정
출력: fix(login): 비밀번호 표시 토글 버튼 동작 수정
```

<a id="5-progressive-disclosure"></a>

## 5. Progressive Disclosure와 크기 규율

### 계층

| 레벨 | 위치 | 내용 | 크기 제한 |
|------|------|------|----------|
| 1 | `SKILL.md` | 개요, 핵심 규칙, 참조 안내 | < 500줄 |
| 2 | `references/` | 상세 규칙, 패턴, 예시 | 제한 없음 (300줄 초과 시 목차) |
| 3 | `templates/` | 재사용 템플릿 | 필요에 따라 |
| 4 | `scripts/` | 공통 유틸리티 스크립트 | 3회 이상 반복 시 |

### 방식 1: 업무 분야별로 파일을 나눈다

```
bigquery-skill/
├── SKILL.md (개요 + 업무 분야 선택 지침)
└── references/
    ├── finance.md (매출, 청구 지표)
    ├── sales.md (영업 기회, 파이프라인)
    └── product.md (API 사용량, 기능)
```

사용자가 매출을 물으면 `finance.md`만 불러온다.

### 방식 2: 필요한 경우에만 상세 지침을 읽는다

```markdown
## 문서 편집
간단한 편집은 XML을 직접 수정한다.
**변경 내용 추적이 필요하면** [REDLINING.md](references/redlining.md)를 참고한다.
```

### 방식 3: 큰 레퍼런스에는 목차를 넣는다

300줄이 넘는 레퍼런스 파일은 상단에 목차를 둔다.

### 크기 규율

- `SKILL.md` < 500줄 — 초과분은 `references/`로 분리한다(SKL-004 토큰 예산도 함께 확인).
- `references/` 파일은 `{prefix}-{topic}.md` 네이밍을 따른다(SKL-006).
- 레퍼런스가 5개 이상이면 `_sections.md` 인덱스 파일 추가를 권장한다(SKL-011).

<a id="6-bundling"></a>

## 6. 스크립트 번들링 판단 기준

테스트를 실행한 에이전트의 작업 기록(트랜스크립트)을 살펴본다. 아래 일이 반복되면 스크립트나 절차를 스킬에 포함한다.

| 반복되는 일 | 조치 |
|------------|------|
| 테스트 세 건 모두에서 같은 보조 스크립트를 만든다 | 스크립트를 `scripts/`에 넣는다 |
| 매번 같은 `pip install`/`npm install`을 실행한다 | 스킬에 의존성 설치 단계를 적는다 |
| 매번 같은 다단계 처리 절차를 따른다 | 스킬 본문에 표준 절차를 적는다 |
| 비슷한 오류 뒤 매번 같은 방법으로 우회한다 | 알려진 문제와 해결 방법을 적는다 |

스킬에 포함한 스크립트는 반드시 직접 실행해 검증한다.

<a id="7-schemas"></a>

## 7. 데이터 스키마 표준

스킬 사이에서 데이터를 일관되게 주고받고, 하네스로 만든 스킬을 테스트·평가할 때 같은 스키마를 쓴다([skill-testing-guide.md](skill-testing-guide.md) 참조).

### `eval_metadata.json`

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "사용자의 작업 프롬프트",
  "assertions": [
    "산출물에 X가 포함되어 있다",
    "Y 형식으로 파일이 생성되었다"
  ]
}
```

### `grading.json`

```json
{
  "expectations": [
    {
      "text": "산출물에 '서울'이 포함되어 있다",
      "passed": true,
      "evidence": "세 번째 단계에서 '서울 지역 데이터 추출'을 확인했다"
    }
  ],
  "summary": { "passed": 1, "failed": 0, "total": 1, "pass_rate": 1.0 }
}
```

**필드명 주의:** `text`, `passed`, `evidence`를 정확히 사용한다. `name`/`met`/`details`처럼 바꾸지 않는다.

### `timing.json`

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

서브에이전트 완료 알림이 오면 `total_tokens`와 `duration_ms`를 **즉시** 저장한다. 두 값은 알림 시점에만 확인할 수 있고 이후 복구할 수 없다.

<a id="8-excluded"></a>

## 8. 스킬에 넣지 않을 내용

- `README.md`, `CHANGELOG.md`, `INSTALLATION_GUIDE.md` 같은 부가 문서 (사용자용 문서는 플러그인 루트 README에 둔다)
- 스킬을 만드는 과정에서만 필요한 정보(테스트 결과, 반복 수정 이력 — 이력은 git 커밋 본문에 남긴다)
- 사용자를 위한 설명서(스킬은 AI 에이전트가 따르는 지시서다)
- Claude가 이미 아는 일반 프로그래밍 지식
- 특정 프로젝트의 일시적 상태
- v1에서만 쓰던 항목(`TeamCreate`/`TeamDelete`, 실험용 에이전트 팀 플래그, 모든 에이전트에 일괄 지정하는 `model`) — 모델은 업무 특성 기반 티어로 고르고 선택 이유를 주석으로 남긴다

<a id="9-reuse"></a>

## 9. 스킬 재사용 설계

새 스킬을 만들기 전에 기존 스킬과 기능을 비교한다 — 프로젝트 `.claude/skills/`와 본 마켓플레이스의 `plugins/*/skills/` 모두. 하네스를 여러 번 구축·확장하면 같은 기능의 스킬이 이름만 달리해 쌓인다. 이 판정은 `SKILL.md`의 **재사용 우선 게이트**(재사용/확장/신규)와 같은 기준이다.

| 기존 스킬과의 관계 | 조치 |
|------|------|
| 기존 스킬이 새 기능을 모두 포함한다 | 새로 만들지 않고 기존 스킬을 에이전트에 연결한다 |
| 일부만 겹치고, 기존 스킬을 일반화하면 새 기능까지 맡을 수 있다 | 기존 스킬을 일반화해 확장한다 |
| 일부 겹치지만 도메인을 의도적으로 특화했다 | 별도 스킬로 새로 만든다 |
| 기능 범위가 전혀 다르다 | 새로 만든다 |

**원칙:** 한 스킬이 한 가지 역할에 집중할수록 재사용하기 쉽고 중복이 줄어든다. 역할이 둘 이상이면 나눌 수 있는지 먼저 검토한다.

### 어디까지 일반화할지

일반화는 끝없이 할 수 있으므로 스킬이 맡기로 한 책임 범위에서 멈춘다. 의도한 도메인 특화는 남기고, 우연히 붙은 종속만 걷어낸다. 예: "핀테크 리스크 평가 PDF" 스킬을 일반화한다면 —

| 걷어낸 종속 | 결과 |
|------|------|
| 핀테크 | "평가 결과 PDF". 책임 범위가 평가 보고서라면 여기서 멈춘다 |
| 평가 | "PDF 서식 작성". 같은 기능의 스킬이 이미 있으면 새로 만들지 않고 그 스킬을 쓴다 |

책임 범위를 처음부터 "핀테크 리스크 평가"로 정했다면 일반화하지 않고 별도 스킬로 둔다.

기존 스킬을 확장하면 그 스킬을 쓰는 에이전트의 동작도 바뀔 수 있다. 확장 전에 어느 에이전트가 이 스킬을 쓰는지 확인하고, 넓어진 사용 범위를 `description`에 반영한다(이중언어 규약·1,400자 한도 유지).

<a id="10-flow-scaffolding"></a>

## 10. flow-scaffolding 연동

harness 플러그인의 `skills/flow-scaffolding/` 템플릿을 활용한다.

- `templates/skill.md` — 스킬 기본 템플릿
- `templates/agent.md` — 에이전트 기본 템플릿
- `templates/team-agent.md` — 팀 에이전트 템플릿 (`## Team Communication Protocol` 포함)
- `templates/orchestrator-skill.md` — 오케스트레이터 스킬 템플릿

`/create-flow`로 컴포넌트를 생성하면 이 템플릿이 자동 적용되고, 생성 후 `/verify-flow`로 SKL-* 규칙을 검증한다.
