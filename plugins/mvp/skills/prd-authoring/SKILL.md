# MVP PRD 작성 표준

> PRD는 사람이 읽는 문서이자 **루프 엔진의 입력 데이터**다.
> prd.md의 모호함은 Stage 4에서 게이트 실패·반증 불가로 되돌아온다.
> "완료 판정은 모델이 아니라 하네스가 한다" — AC가 검증형이어야 하네스가 판정할 수 있다.

## When to Apply

다음 상황에서 이 스킬을 참조한다:

- `product-strategist`가 Stage 1(기획)에서 `.planning/prd.md`와 `.planning/prd.json` 초안을 작성할 때
- `mvp-verifier`가 Stage 1 PRD 반증(범위 비대·검증 불가 AC·측정 불가 지표·페르소나-스토리 불일치 탐색)을 수행할 때
- G1 스코프 승인 게이트에서 받은 사용자 피드백을 반영해 PRD를 수정할 때
- `/mvp-gate` 실행 결과 `gate-prd.sh`가 실패하여 원인을 진단·교정할 때
- Stage 4 루프 중 BLOCKED → 스코프 재협상으로 `product-strategist`가 재투입되어 스토리를 분할·축소할 때

## 1. 핵심 규칙

| # | 규칙 | 집행 주체 |
|---|------|-----------|
| R1 | prd.md는 필수 5섹션 헤딩을 **정확한 문자열**로 포함한다 (§2) | `gate-prd.sh` grep |
| R2 | 스토리 수는 **3개 이상 10개 이하** | `gate-prd.sh` jq |
| R3 | 스토리 id는 `S-01` 형식(대문자 S + 하이픈 + 2자리 숫자), 중복 금지 | `gate-prd.sh` jq |
| R4 | 모든 AC는 Given-When-Then 검증형 문장 — 실행·관찰로 거짓 판명 가능해야 함 (§3) | `mvp-verifier` 반증 |
| R5 | `passes`는 작성 시점에 전부 `false`. true 전환은 verified 마커 이후 루프만 수행 | `prd-guard.sh` 훅 |
| R6 | 1 스토리 = 1 루프 반복에 끝나는 크기 (§6) | `mvp-builder` 반복 단위 |
| R7 | 결제·푸시알림·관리자 기능은 디폴트 Out — In으로 올리려면 근거 명시 (§5) | G1 사용자 게이트 |
| R8 | 성공 지표는 측정 방법이 함께 적힌 수치여야 한다 | `mvp-verifier` 반증 |

## 2. prd.md 필수 섹션

`gate-prd.sh`가 아래 헤딩을 **정확한 문자열로 grep**하므로 변형(띄어쓰기·영문·이모지) 금지.

| 헤딩(정확 문자열) | 내용 | 작성 기준 |
|-------------------|------|-----------|
| `## 문제 정의` | 누가, 어떤 상황에서, 무엇 때문에 고통받는가 | 해결책 언급 없이 문제만. 3문장 이내 |
| `## 페르소나` | 핵심 사용자 1~2명: 이름·상황·동기·현재 우회책 | 모든 스토리의 주어가 이 페르소나여야 함 |
| `## 범위` | `### In` / `### Out` 하위 섹션 필수 | Out이 비어 있으면 범위 비대 신호 |
| `## 유저 스토리` | 스토리별 제목 + AC 목록 (prd.json과 id 일치) | AC는 §3 규칙 준수 |
| `## 성공 지표` | 수치 목표 + 측정 방법 + 측정 시점 | 허영 지표 금지 (§7) |

골격 예시:

```markdown
# PRD: 팀 점심 메뉴 추천

## 문제 정의
5인 이하 소규모 팀은 매일 점심 메뉴 결정에 평균 15분을 소비하며,
결정 피로로 같은 식당만 반복 방문한다.

## 페르소나
- 김팀장(34): 점심 결정권을 떠안은 팀 리더. 현재 우회책은 사다리타기 앱.

## 범위
### In
- 메뉴 후보 등록, 랜덤 추천, 최근 7일 중복 제외
### Out
- 결제 연동, 푸시 알림, 관리자 대시보드, 식당 리뷰 크롤링

## 유저 스토리
### S-01 메뉴 후보 등록
- AC-1: Given 빈 후보 목록일 때 When "김밥천국"을 등록하면
  Then 201이 반환되고 GET /menus 응답에 해당 항목이 포함된다

## 성공 지표
- 추천 버튼 클릭 → 결정 완료까지 60초 이내 (서버 로그 타임스탬프 차이로 측정, 출시 2주 후 집계)
```

## 3. AC 작성 규칙 — Given-When-Then

AC는 `mvp-verifier`가 **직접 실행해 반증을 시도하는 대상**이다. 반증 가능 = 절차를 수행했을 때
거짓으로 판명될 수 있는 문장. 형용사로는 반증할 수 없다.

| 규칙 | 설명 |
|------|------|
| 1 AC = 1 관찰 결과 | Then에 결과가 2개 이상이면 AC를 분리 |
| 측정 불가 형용사 금지 | "편리하게", "직관적으로", "빠르게" → 수치·상태로 치환 |
| 실행 절차 도출 가능 | 문장만 읽고 curl/테스트/화면 조작 절차를 만들 수 있어야 함 |
| UI도 관찰 가능하게 | "보기 좋다" 대신 "로딩 중 스켈레톤이 표시된다" |
| 엣지케이스 1개 이상 | 스토리마다 정상 경로 외 빈 입력·중복·권한 등 1개 포함 |

### 나쁜 예

```text
AC: 사용자가 메모를 편리하게 조회할 수 있다
```

"편리하게"는 실행으로 거짓 판명이 불가능 → mvp-verifier가 반증을 시작조차 못 하고,
mvp-builder는 아무 구현이나 통과라고 주장할 수 있다.

### 좋은 예

```text
AC-1: Given 등록된 메모 3건이 있을 때
      When GET /memos 를 호출하면
      Then 200과 함께 3건이 createdAt 내림차순으로 반환된다
AC-2: Given 등록된 메모가 0건일 때
      When GET /memos 를 호출하면
      Then 200과 빈 배열 []이 반환된다
```

각 문장이 그대로 테스트 케이스가 되고, mvp-verifier는 정렬을 뒤집거나 0건 상태를 만들어 반증을 시도할 수 있다.

## 4. prd.json 스키마 + jq 검증식

위치: `.planning/prd.json`. 루프 엔진(`mvp-loop-stop-hook.sh`)과 `prd-guard.sh`가 직접 읽는다.

```json
{
  "stories": [
    {
      "id": "S-01",
      "title": "메뉴 후보 등록",
      "acceptance": [
        "Given 빈 후보 목록일 때 When POST /menus 로 \"김밥천국\"을 등록하면 Then 201이 반환되고 GET /menus 응답에 포함된다",
        "Given 동일 이름이 이미 있을 때 When 같은 이름을 등록하면 Then 409가 반환된다"
      ],
      "passes": false
    },
    {
      "id": "S-02",
      "title": "랜덤 메뉴 추천",
      "acceptance": [
        "Given 후보 3건이 있을 때 When GET /recommend 를 호출하면 Then 후보 중 1건이 반환된다"
      ],
      "passes": false
    },
    {
      "id": "S-03",
      "title": "최근 7일 중복 제외",
      "acceptance": [
        "Given 어제 추천된 메뉴가 있을 때 When GET /recommend 를 호출하면 Then 해당 메뉴는 반환되지 않는다"
      ],
      "passes": false
    }
  ]
}
```

작성 직후 아래 검증식을 전부 통과해야 한다 (`gate-prd.sh`가 동일 검사를 수행):

```bash
# 스토리 수 3~10
jq -e '.stories | length >= 3 and length <= 10' .planning/prd.json

# 필수 키 4종 존재
jq -e '.stories | all(has("id") and has("title") and has("acceptance") and has("passes"))' .planning/prd.json

# id 형식 S-NN + 중복 없음
jq -e '.stories | all(.id | test("^S-[0-9]{2}$"))' .planning/prd.json
jq -e '.stories | map(.id) | length == (unique | length)' .planning/prd.json

# AC 1개 이상, passes 초기값 전부 false
jq -e '.stories | all((.acceptance | length) >= 1)' .planning/prd.json
jq -e '.stories | all(.passes == false)' .planning/prd.json
```

`passes`를 손으로 `true`로 바꾸지 않는다 — `.planning/verified/{id}` 마커 없는 마킹은
`prd-guard.sh`가 exit 2로 차단하고 `false`로 되돌린다.

## 5. 스코프 컷 기준 — 2주 룰

**"첫 사용자가 첫 가치를 얻는 순간"까지만 In.** 그 경험에 필요 없는 모든 것은 Out.
기준 시간: 루프 가동 기준 2주 내 완주 가능 분량(스토리 10개 이하가 같은 제약의 수치 표현).

### 디폴트 Out 목록

| 기능 | Out인 이유 | MVP 대체재 |
|------|-----------|------------|
| 결제 | PG 연동·정산·환불은 그 자체로 2주 이상 | 무료 공개 또는 수기 정산 |
| 푸시 알림 | 인증서·토큰·수신동의 인프라 비용 | 인앱 표시, 필요 시 이메일도 보류 |
| 관리자 기능 | 운영자는 아직 개발자 본인 | DB 직접 조회 + 시드 스크립트 |
| 소셜 로그인 2종 이상 | 제공자별 콘솔 설정 반복 | 이메일 1종 또는 익명 세션 |
| 다국어(i18n) | 첫 사용자는 단일 언어권 | 한국어 고정 |
| 검색·필터 고도화 | 데이터 10건일 때 불필요 | 단순 목록 + 클라이언트 필터 |

디폴트 Out을 In으로 올릴 때는 `### In` 항목 옆에 근거 1줄을 명시한다
(예: "결제 In — 유료 결제 전환율 자체가 검증 가설이므로").

### In/Out 판단 질문 3개

1. 이 기능이 없으면 첫 사용자가 핵심 가치를 경험하지 못하는가? → 아니오면 Out
2. 이 기능 없이 수동·우회로 1주일 버틸 수 있는가? → 예면 Out
3. 이 기능이 성공 지표 측정에 필수인가? → 아니오면 Out

## 6. 스토리 크기 가이드 — 1 스토리 = 1 루프 반복

Stage 4 루프는 매 반복 **미완 스토리 1개**를 잡아 테스트 작성 → 최소 구현 → 게이트 그린 →
커밋으로 닫는다. 한 반복(단일 세션 컨텍스트) 안에 닫히지 않는 스토리는 루프를 정체시키고
no-progress 가드(연속 2회 동일 실패 시그니처)에 걸린다.

분할 신호:

| 신호 | 조치 |
|------|------|
| AC가 6개 이상 | 정상 경로/엣지케이스 축으로 2개 스토리로 분할 |
| 제목에 "그리고"·"및"이 등장 | 접속사 기준으로 분할 |
| 화면 2개 + API 2개 이상에 걸침 | 화면 단위 또는 API 단위로 분할 |
| 다른 스토리 2개 이상에 선행 의존 | 의존 대상을 먼저 배치하고 id 순서 조정 |

### 나쁜 예

```text
S-01 사용자는 회원가입하고 로그인하고 프로필을 수정할 수 있다
```

### 좋은 예

```text
S-01 이메일 회원가입   (AC 2개: 성공·중복 이메일 409)
S-02 로그인과 세션 발급 (AC 2개: 성공·잘못된 비밀번호 401)
S-03 프로필 닉네임 수정 (AC 2개: 성공·비로그인 401)
```

## 7. 안티패턴

`mvp-verifier`가 Stage 1 반증에서 우선 탐색하는 3대 패턴. 작성자는 셀프 체크로 선제 제거한다.

| 안티패턴 | 증상 | 반증 관점 | 교정 |
|----------|------|-----------|------|
| 범위 비대 | 스토리 10개 초과 시도, Out 섹션 빈약, 디폴트 Out 기능이 근거 없이 In | "이 스코프가 틀렸다면 왜? — 2주 내 완주 불가" | §5 질문 3개로 컷, 스토리 병합 아닌 **삭제** |
| 모호 AC | 형용사 AC, Then 없는 문장, 실행 절차 도출 불가 | "이 AC는 어떤 구현이든 통과 주장 가능" | §3 형식으로 재작성, 수치·상태 코드 명시 |
| 허영 지표 | "가입자 1만 명", 측정 방법 없는 목표, 행동과 무관한 누적 수치 | "측정 불가 또는 가치 검증과 무관" | 행동 지표로 치환: 재방문율·작업 완료 시간·완료율 + 측정 방법 병기 |

### 허영 지표 나쁜 예 / 좋은 예

```text
BAD : 출시 후 가입자 10,000명 달성          ← 측정 시점·방법 없음, 가치 검증과 무관
GOOD: 출시 2주 후, 가입자 중 7일 내 재방문율 30% 이상 (세션 로그 user_id 기준 집계)
```
